·  Engineering — Git & GitHub

The model first, the commands second.

Most Git confusion comes from learning commands without the model underneath them. This guide builds the model — snapshots, refs, three trees — then layers the daily loop, branching, recovery, and the GitHub platform on top: pull requests, tokens, Pages and Actions. Every command here is one you will actually type.

01  The mental model

Git stores snapshots, not changes.

Git is the version control system on your machine. GitHub is a hosting platform built around it — issues, reviews, CI, permissions. Git works perfectly without GitHub; GitHub is meaningless without Git. Keep the two separate in your head.

Objects

Every time you commit, Git stores a complete snapshot of the tracked files, addressed by a SHA-1 hash. It does not store diffs — diffs are computed on demand when you ask for them.

ObjectIsHolds
blobfile contentsthe bytes of one file, no name
treea directorynames, modes, and pointers to blobs and other trees
commita snapshotone root tree, parent commit(s), author, date, message
taga markera named, optionally signed pointer to a commit

Because each commit names its parent, history is a directed graph. A merge commit simply has two parents.

Refs and HEAD

A branch is not a container. It is a movable pointer to one commit, stored as a file under .git/refs/heads/. Committing moves the pointer forward. That is the whole mechanism.

  • HEAD — a pointer to the branch you are currently on.
  • Detached HEAD — HEAD points straight at a commit instead of a branch. Commits made here belong to no branch and are easy to lose.
  • origin/main — a remote-tracking ref: your local record of where main was on the remote the last time you fetched. It only moves when you fetch or push.

The three trees

Nearly every confusing Git moment is a question of which of these three you are touching.

TreeAlso calledWhat it is
working treeyour fileswhat the editor sees on disk
indexstaging areathe draft of the next commit
HEADlast committhe snapshot you committed most recently

git add copies working tree → index. git commit copies index → new commit. git status is simply a report of the differences between the three.

Read status properly“Changes to be committed” is the index. “Changes not staged for commit” is the working tree. “Untracked files” are files Git has never seen and will ignore until you add them.

02  The daily loop

Five commands cover most days.

Set your identity once per machine, then the loop is status, add, commit, push.

# one-off setup
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase true   # linear history on pull

# the loop
git status
git add index.html styles.css   # or: git add -p  (stage hunk by hunk)
git commit -m "Add contact form validation"
git push

Starting a repository

git clone https://github.com/user/repo.git   # existing

# or, from a folder you already have
git init
git add .
git commit -m "Initial commit"
git remote add origin https://github.com/user/repo.git
git push -u origin main    # -u sets the upstream, once

Fetch, pull, push

  • git fetch — downloads new commits and updates origin/*. Changes nothing in your working tree. Always safe.
  • git pull — fetch, then merge (or rebase) into your branch. Can produce conflicts.
  • git push — uploads your commits and moves the remote branch. Rejected if the remote has commits you do not have; fetch and integrate first.
Fetch before you judgeIf a colleague says a change is on main and you cannot see it, you are reading a stale origin/main. Run git fetch first, then look again.

Ignoring files

.gitignore stops Git offering to track matching paths. It has no effect on files already tracked — those must be untracked explicitly.

# .gitignore
node_modules/
.env
*.log
dist/
!dist/.gitkeep      # ! re-includes an exception

# stop tracking a file already committed, keep it on disk
git rm --cached .env
git commit -m "Stop tracking local environment file"
Ignoring is not removingAdding a secret to .gitignore after committing it does nothing — the secret is still in history and still public. Rotate the credential, then clean history separately.

03  Branching & integrating

Cheap pointers, deliberate merges.

Branches cost nothing — creating one writes a 41-byte file. Branch for every unit of work.

git switch -c feature/contact-form   # create and move onto it
git switch main                      # move back
git branch -a                        # list, including remotes
git branch -d feature/contact-form   # delete once merged

git switch and git restore replaced the overloaded git checkout, which did both jobs. Older material will use checkout throughout; it still works.

Merge vs rebase

mergerebase
Doesjoins two histories with a new commitreplays your commits on a new base
Historytrue, branchinglinear, tidied
Hashespreservedrewritten — they are new commits
Use onanythingyour own unpushed work only

A fast-forward is the third case: if your branch has not diverged, Git just slides the pointer forward with no merge commit at all.

The golden ruleNever rebase commits that others have already pulled. Rebasing replaces commits with new ones, so anyone holding the originals now has a divergent history and a painful reconciliation.

Resolving a conflict

A conflict means both sides changed the same lines and Git will not guess. It marks the file and waits.

<<<<<<< HEAD
<h1>Contact us</h1>
=======
<h1>Get in touch</h1>
>>>>>>> feature/contact-form
  1. Edit the file to the version you actually want. Delete all three marker lines.
  2. git add <file> to mark it resolved.
  3. git commit (merge) or git rebase --continue (rebase).
  4. Escape hatch at any point: git merge --abort or git rebase --abort.

Moving single commits

git cherry-pick a1b2c3d      # copy one commit onto the current branch
git rebase -i HEAD~5         # reword, squash, drop, reorder the last 5

04  Undoing & recovering

Almost nothing committed is ever lost.

Choose the tool by asking two questions: has it been committed, and has it been pushed?

SituationCommand
Discard edits to a filegit restore <file>
Unstage, keep the editsgit restore --staged <file>
Fix the last commit (unpushed)git commit --amend
Undo a pushed commitgit revert <sha>
Park work in progressgit stash / git stash pop
Find a lost commitgit reflog

reset, and its three modes

git reset moves the branch pointer backwards. The flag decides how much else it drags with it.

ModeMoves HEADIndexWorking tree
--softyesuntoucheduntouched
--mixedyesresetuntouched (default)
--hardyesresetoverwritten — edits lost
git reset --soft HEAD~1
Undoes the last commit but leaves every change staged — the standard way to redo a commit you split wrongly.

revert vs reset

reset rewrites history; revert adds a new commit that undoes an old one. On a shared branch, always revert — it is the only option that does not break everyone else's clone.

The reflog

Git records every position HEAD has held, for around 90 days, whether or not the commit is still reachable from a branch. This is the safety net behind a bad reset, a deleted branch, or a rebase gone wrong.

git reflog                 # find the sha from before the mistake
git switch -c rescue a1b2c3d
The one genuinely destructive caseUncommitted work discarded by git reset --hard or git restore was never in an object, so the reflog cannot bring it back. Commit early — a bad commit is trivially fixable, lost edits are not.

05  Remotes, forks & pull requests

Where GitHub actually begins.

A remote is a named URL. origin is only a convention for “the one I cloned from”.

git remote -v
git remote add upstream https://github.com/original/repo.git
git remote set-url origin git@github.com:user/repo.git

Clone or fork?

  • Clone when you have write access — branch inside the repository.
  • Fork when you do not — GitHub copies the repo under your account, you push there, then open a pull request back. Add the original as upstream to stay current.

The pull request

A PR is a request to merge one branch into another, plus the conversation, review and checks attached to it. It is a GitHub construct, not a Git one.

  1. Branch, commit, git push -u origin feature/x.
  2. Open the PR; describe the why, not the diff — the diff is already visible.
  3. Reviewers comment, request changes, or approve. Push more commits to the same branch and the PR updates itself.
  4. Merge, then delete the branch.
Merge optionResultSuits
Merge commitkeeps every commit plus a merge nodelong-lived, auditable branches
Squash and mergeone tidy commit on the targetmost feature work
Rebase and mergecommits replayed, no merge nodestrictly linear histories

Protecting the default branch

Branch protection rules (now rulesets) can require a PR, a minimum number of approvals, passing status checks, and signed commits, and can block force pushes. On a solo repository, requiring status checks to pass is still worth it — it is what stops a broken build reaching production.

Tags and releases

git tag -a v1.2.0 -m "Contact form live"
git push origin v1.2.0

A GitHub release wraps a tag with notes and downloadable assets. Tag with semantic versioning: MAJOR.MINOR.PATCH — breaking, additive, fix.

06  Authentication

Tokens, keys and where they live.

GitHub stopped accepting account passwords for Git operations in 2021. Three routes remain.

MethodBest forNotes
SSH keyyour own machinesno expiry, no copy-pasting, survives token rotation
HTTPS + PATscripts, containers, CIexpires; scope it narrowly
gh CLIinteractive setuphandles the OAuth flow and the credential store for you

SSH, once

ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub        # paste into GitHub → Settings → SSH keys
ssh -T git@github.com            # expect a greeting, not a shell

Personal access tokens

  • Fine-grained — pinned to named repositories with per-permission grants (contents: read/write, pages: write, and so on) and a mandatory expiry. Prefer these.
  • Classic — broad scopes such as repo across everything you can reach. Only where fine-grained is not yet supported.

A token is used as the password in an HTTPS push. Never commit one, never paste one into a URL you might save, and set the shortest expiry that will do the job.

If a token leaksRevoke it first, before cleaning history. Revocation is instant and total; history rewriting is slow, breaks clones, and cannot recall what has already been scraped. Then rotate, then rewrite with git filter-repo if the value must go.

gh, the command line client

gh auth login
gh repo create my-project --public --source=. --push
gh pr create --fill
gh pr checks
gh release create v1.2.0 --generate-notes

07  GitHub Pages

A repository, served as a site.

Pages publishes static files from a repository to https://<user>.github.io/<repo>/. Under Settings → Pages the source is either a branch (root or /docs) or a GitHub Actions workflow.

  • index.html at the published root is the landing page; every other file is served by path.
  • Use relative links — an absolute /audio/clip.mp3 resolves to the user site, not the project subpath, and will 404.
  • Add an empty .nojekyll file at the root to skip Jekyll processing. Without it, anything beginning with an underscore is silently dropped.
  • A custom domain is a CNAME file plus DNS; enable Enforce HTTPS once the certificate has been issued.
  • Publication takes a minute or two, and the CDN caches hard. If an update seems missing, load with cache disabled before assuming the deploy failed.
Public means publicPages on a free plan serves from a public repository. Everything in it — including anything committed once and deleted later — is readable by anyone. Never put keys, client names or draft commercials in a Pages repo.

08  Actions

Automation that lives in the repo.

A workflow is a YAML file in .github/workflows/. GitHub watches for the events you name and runs the jobs on a hosted machine.

name: Validate
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:        # adds a manual "Run workflow" button

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm test
TermMeans
onthe events that trigger the run
joba unit that gets its own fresh runner; jobs run in parallel unless needs: chains them
stepeither uses: a published action or run: a shell command
secretsencrypted values, read as ${{ secrets.NAME }}, never printed in logs

Each job starts from a clean runner, so state does not carry across jobs — pass it explicitly with artefacts or job outputs. Cache dependencies rather than reinstalling them on every run.

Least privilegeSet permissions: explicitly in the workflow. The automatic GITHUB_TOKEN should get only what the job needs — a Pages deploy needs pages: write and id-token: write, and nothing more.

09  Conventions worth adopting

Habits that make history readable.

Commit messages

Imperative mood, capital first letter, no full stop, under about 50 characters. Complete the sentence “If applied, this commit will …”. Put the reasoning in the body, separated by a blank line.

Add rate limiting to the enquiry endpoint
Not: “added rate limiting”, “fixes”, “wip”, “updates”.

Conventional Commits adds a machine-readable prefix — feat:, fix:, docs:, chore:, with ! for a breaking change — which lets tooling derive version numbers and changelogs.

Commit and PR size

One logical change per commit; one reviewable concern per PR. Review quality falls off a cliff past a few hundred changed lines — a large PR gets approved, not read.

Repository furniture

  • README.md — what it is, how to run it, how to deploy it. Written for someone arriving cold.
  • .github/CODEOWNERS — paths mapped to reviewers, requested automatically.
  • .github/pull_request_template.md — the questions every PR should answer.
  • A licence file if the repository is public and you want the terms to be unambiguous.

Branching strategies

StrategyShapeSuits
Trunk-basedshort branches straight off main, merged dailysmall teams, continuous deployment
GitHub Flowbranch → PR → review → merge → deploymost web work; the sane default
Git Flowdevelop, release and hotfix branchesversioned software with supported releases
