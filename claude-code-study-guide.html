·  Engineering — Claude & Claude Code

The harness first, the commands second.

Claude Code is not a chat box with file access. It is an agentic harness: a loop, a set of tools, a permission system, and an extension layer you configure. Learn the harness and the commands follow. This guide builds the model — loop, context, permissions — then layers the extension surface on top: skills, subagents, agent teams, hooks, MCP, and the Agent SDK. Verified against the documentation on 2026-08-05.

01  The landscape

Three different things are called “Claude”.

Conflating them is the most common source of confusion. They share a model and, increasingly, a configuration substrate — but they are separate products with separate boundaries.

LayerWhat it isReached via
Claude appsChat, Projects, Artifacts, memory, connectorsclaude.ai, desktop, mobile, Cowork, Claude in Chrome / Excel / PowerPoint, Claude Design, Claude Tag
Claude CodeAgentic harness with filesystem, shell, git and browser toolsCLI, VS Code, JetBrains, Desktop app, web, Slack, mobile
Claude PlatformRaw model access and the Agent SDKAPI, Bedrock, Google Agent Platform, Microsoft Foundry

Models and aliases

AliasModelPosition

sonnetClaude Sonnet 5Workhorse; extended-context variant available
haikuClaude Haiku 4.5Fast and cheap — good for fan-out subagents
fableClaude Fable 5Mythos-tier with additional safeguards; not available as the advisor model

opusplan plans with Opus and executes with a cheaper model. --fallback-model sonnet,haiku sets a chain tried in order when the primary is overloaded or retired.

Effort — the lever most people never touch

Effort controls how much reasoning the model applies per turn. It is set with /effort or --effort and is independent of extended thinking: you can run low effort with thinking on, or maximum effort without it.

LevelGood for
lowFile lookups, listing directories
mediumRoutine edits, standard tasks
highRefactors, debugging
xhighCoding and agentic work — the recommended default on current models
maxMulti-step problems needing deep analysis. Session-only
ultracodeStarts at xhigh and lets Claude escalate into a parallel workflow. Session-only

ultrathink in a prompt buys one-off deep reasoning without changing the session default. Fast mode (/fast) is a separate axis again — it trades cost for latency.

02  The agentic loop

Evaluate, call tools, repeat until done.

Every Claude Code session — and every Agent SDK agent — runs the same cycle. Understanding it is what turns unpredictable behaviour into debuggable behaviour.

  1. Receive prompt. The model gets your prompt plus the system prompt, tool definitions, and the conversation so far.
  2. Evaluate and respond. It emits text, one or more tool calls, or both.
  3. Execute tools. The harness runs them and feeds results back. Hooks can intercept here.
  4. Repeat. Steps 2 and 3 cycle. Each full cycle is one turn.
  5. Return. The loop ends when Claude produces a response with no tool calls.

A quick question is one or two turns. “Refactor the auth module and update the tests” can be dozens of tool calls across many turns, with the approach adjusting after each result.

The single highest-leverage habitGive Claude something to verify against — tests, a type-checker, a linter, a running app. Agentic quality is bounded by the feedback loop available inside the turn, not by how well you worded the prompt.

Built-in tools

CategoryTools
filesRead, Edit, Write
searchGlob, Grep
executionBash (PowerShell on Windows)
webWebSearch, WebFetch
discoveryToolSearch — loads tool definitions on demand
orchestrationAgent, Skill, AskUserQuestion, TaskCreate, TaskUpdate
navigationLSP — inactive until a code intelligence plugin is installed

Read-only tools run concurrently; anything that modifies state runs sequentially to avoid conflicts.

Working with the loop, not against it

  • Explore, then plan, then code. /plan is read-only, so being wrong there is cheap.
  • Delegate, don’t dictate. Describe the outcome and the constraints; let it choose the path.
  • Interrupt early. Course-correcting at turn two costs a fraction of correcting at turn twenty.
  • Ask it about itself. Claude Code fetches its own documentation map, so questions about its features are answered from current docs rather than training data.

03  The extension layer

Each feature plugs into a different part of the loop.

Everything you can add answers a different question: what does Claude always know, what can it look up, what can it reach, what runs without asking, and how do you ship the lot to a second repository.

FeatureWhat it doesReach for it when
CLAUDE.mdPersistent context, loaded every session“Always do X” conventions
.claude/rules/Same, but scoped to file paths via paths: frontmatterLanguage- or directory-specific rules
skillsReusable knowledge or an invocable workflowYou’ve pasted the same playbook three times
subagentsIsolated context that returns a summaryA side task would flood your window
agent teamsIndependent sessions that message each otherTeammates need to disagree and coordinate
hooksDeterministic action on a lifecycle eventIt must happen every time
MCPExternal services and dataClaude can’t see the system it needs
artifactsPrivate interactive web page from session outputThe output is visual or shareable
pluginsPackaging and distribution for all of the aboveA second repo needs the same setup
Request versus enforcement“Never edit .env” written in CLAUDE.md is a request. A PreToolUse hook that blocks the edit is enforcement. If a rule must hold every time, it is a hook, not a sentence in a prompt. This one distinction matters more than any other in this guide.

Skill or subagent?

SkillSubagent
IsReusable instructions or knowledgeAn isolated worker with its own context
BenefitShare content across contextsContext isolation — only a summary returns
Best forReference material, invocable workflowsReading many files, parallel work

They combine: a subagent can preload skills via its skills: field, and a skill can run in isolated context with context: fork.

Subagent or agent team?

SubagentAgent team
CommunicationReports back to the lead onlyTeammates message each other directly
CoordinationThe lead manages all workShared task list, self-coordinating
Token costLower — results summarisedHigher — each teammate is a separate instance

The transition point is concrete: you are running parallel subagents and hitting context limits, or your subagents need to talk to each other. Agent teams are experimental and off by default.

Layering and precedence

When to add what

04  Context & cost

Everything you add is charged, some of it on every request.

Context is the scarce resource. Too much doesn’t only fill the window — it adds noise, so skills stop triggering correctly and conventions get lost.

FeatureWhen it loadsCost
CLAUDE.mdSession start, full contentCharged on every request
skillsDescriptions at start, body on useLow; zero with disable-model-invocation: true
MCPTool names at start, schemas deferredLow — tool search is on by default
code intelAfter edits and on lookupLow, often net negative — replaces file reads
subagentsOn spawn, fresh windowIsolated from the main session
hooksOn trigger, outside the conversationZero unless they return output
Keep CLAUDE.md under 200 linesIt is the only item on that table charged in full on every single request. Reference material belongs in skills, which load on demand; path-specific rules belong in .claude/rules/, which load only when matching files are touched.

Prompt caching — what breaks it

The static prefix of your session is cached. Some actions invalidate that cache and force a full re-read of history; others don’t. The split is not intuitive.

Invalidates the cacheKeeps the cache
ActionsSwitching models · changing effort · toggling fast mode · connecting or disconnecting an MCP server · enabling or disabling a plugin · denying an entire tool · compacting · upgrading Claude CodeEditing files · editing CLAUDE.md mid-session · changing output style · changing permission mode · invoking skills and commands · /recap · rewinding

Two flags exist specifically to protect the cache: /cd moves the session to a new directory without rebuilding the system prompt, and --exclude-dynamic-system-prompt-sections moves machine-specific sections out of the prompt so the cache is reusable across machines and users — worth it for any scripted fleet workload.

Compaction

When the window fills, the conversation is summarised. Older messages are replaced, so instructions from early in a session can vanish. Three defences:

  • Persistent rules go in CLAUDE.md, not the opening prompt — CLAUDE.md is re-injected every request.
  • Tell the compactor what to keep. It reads CLAUDE.md like any other context, and the header is not a magic string — it matches on intent.
  • Use a PreCompact hook to archive the full transcript before it is summarised away.
# CLAUDE.md
# Summary instructions

When summarizing this conversation, always preserve:
- The current task objective and acceptance criteria
- File paths that have been read or modified
- Test results and error messages
- Decisions made and the reasoning behind them

Cost controls

/context            # colour-grid of what is filling the window
/autocompact 500k   # set when auto-compaction fires
/doctor             # trims CLAUDE.md, flags unused skills/MCP/plugins, finds slow hooks
/insights           # report on your own session patterns and friction
claude -p --max-budget-usd 5.00 "query"   # hard cap; subagent spend counts
Run /doctor on every repoIt deduplicates local CLAUDE.md files against checked-in ones, cuts sections Claude could derive from the codebase anyway, and reports which skills, MCP servers and plugins are costing you context without being used. It reports first and asks before changing anything.

05  Permissions, auto mode & sandboxing

Three independent layers of control.

Permission modes set the posture. Permission rules set the specifics. Sandboxing enforces at the OS level regardless of either. They are not alternatives.

ModeBehaviour
defaultPrompts for each new action. Labelled “Manual” in the UI
acceptEditsAuto-approves file edits and common filesystem commands
planRead-only analysis, produces a plan you approve
autoA model classifier adjudicates; prompts only when it can’t decide
dontAskNever prompts. Pre-approved tools run, everything else is denied
bypassPermissionsSkips checks. Sandbox this — and it cannot run as root on Unix

Cycle modes with Shift+Tab. Protected paths still apply in every mode.

Rule syntax

"Bash(git log *)"      # allow one command family
"Edit(**/src/**)"      # a directory at any depth
"Edit(src/**)"         # only src in the working directory
"mcp__*"               # every MCP tool
"Bash(rm *)"           # deny rule: tool stays available, matching calls denied

A bare tool name in a deny rule removes the tool from context entirely; a scoped rule leaves it available and denies only matching calls. Two different outcomes from similar-looking syntax.

Auto mode

Auto mode replaces prompting with a classifier. It is configurable: you declare trusted infrastructure, state boundaries in conversation, add human checkpoints, and override the block and allow rules. Inspect what you have with:

claude auto-mode defaults --label 'Git Destructive'   # built-in rules as JSON
claude auto-mode config                               # your effective config
claude auto-mode reset --yes                          # back to defaults
/permissions                                          # review recent auto-mode denials

This is the natural home for a tiered-autonomy model: tiers become classifier boundaries plus per-agent hooks, rather than a policy document nobody enforces.

Sandboxing

Separate from permissions entirely: OS-level filesystem and network isolation, with credential masking for environment variables and credential files. Approaches, weakest to strongest: sandboxed Bash tool, the sandbox runtime, dev containers, a custom container, a virtual machine, cloud sessions. For unattended runs, isolation is the answer — not a longer allowlist.

06  Parallel & autonomous work

Five different ways to run more than one thing.

MechanismShape
subagentsIsolated workers inside your session, reporting to the lead
background/background detaches the session; /fork copies it into a new one
agent viewclaude agents — monitor, peek, reply, dispatch, all supervisor-hosted
agent teamsIndependent peers with a shared task list
workflowsA saved script that fans work across subagents deterministically

Agent view — the control plane

claude agents                 # monitor and dispatch
claude agents --json --all    # scriptable session list
claude --bg "investigate the flaky test"
claude attach 7c5dcf5d        # take over in this terminal
claude logs|stop|rm|respawn 7c5dcf5d
claude daemon status          # the supervisor process

Background sessions are hosted by a supervisor, so they outlive the terminal that started them. File edits are isolated per session.

Fan-out

  • /batch <instruction> — decomposes a change into 5–30 units, one background subagent per unit, each in its own worktree, each opening a pull request.
  • Dynamic workflows — Claude writes a script that orchestrates subagents, which you then save, reuse, and distribute in a plugin. Bundled examples include /deep-research.
  • -w <name> — start in an isolated git worktree. Add --tmux for panes.

Keeping work running

CommandShape
/goalKeep working across turns until a stated condition is met
/loopRe-run a prompt on an interval, or self-paced
routinesCloud sessions on a schedule, an API trigger, or a GitHub event
/autofix-prA cloud session that watches a PR and pushes fixes when CI fails
Every loop needs an exit/goal, Stop hooks, TaskCompleted hooks and TeammateIdle hooks can all refuse to let work end. Each needs a condition that can actually be satisfied, and ideally a counter. A gate that can never pass is an agent that never stops spending.

Review

/code-review --fix          # local diff review, applies findings
/code-review ultra          # deep multi-agent cloud review
/review                     # fast read-only pass over a GitHub PR
/security-review            # security vulnerabilities in the diff
claude ultrareview 1234 --json

A documented best practice worth adopting: add an adversarial review step — a second agent whose only job is to attack the first one’s work. It catches more than a longer prompt does.

07  Hooks

The deterministic layer around a probabilistic agent.

A hook has three levels of nesting, and the vocabulary prevents most confusion:

hook event          # the lifecycle point — PreToolUse, Stop, TeammateIdle…
  matcher group     # the filter — "only Bash", "only on resume"
    hook handler    # what runs — command | http | mcp_tool | prompt | agent

Hooks fire wherever Claude Code runs — terminal, IDE, Desktop, web — and inside subagents, where the input carries agent_id and agent_type. All matching handlers run in parallel.

Handler types

TypeRuns
commandA shell command. JSON on stdin, decision via exit code or stdout JSON
httpPOST to a URL. Decision via the response body
mcp_toolA tool on an already-connected MCP server. Never triggers a connection or OAuth flow
promptSingle-turn model evaluation returning a yes/no decision
agentA subagent that can read and grep to verify a condition first. Experimental

The events that can block

EventExit 2 does
PreToolUseBlocks the tool call
PermissionRequestDenies the permission
UserPromptSubmitBlocks the prompt and erases it
Stop / SubagentStopPrevents stopping — the conversation continues
TeammateIdleKeeps an agent-team teammate working
TaskCreated / TaskCompletedRolls back creation / refuses the completion
PostToolBatchHalts the agentic loop before the next model call
ConfigChangeBlocks the change, except policy settings
PreCompactBlocks compaction
WorktreeCreateFails creation — on any non-zero exit, not just 2

Observe-only events include PostToolUse, PostToolUseFailure, SessionStart, Setup, SubagentStart, SessionEnd, Notification, InstructionsLoaded, CwdChanged, DirectoryAdded, FileChanged, PostCompact and StopFailure.

Exit 1 does not blockClaude Code treats exit 1 as a non-blocking error and proceeds — even though 1 is the conventional Unix failure code. Policy hooks must exit 2. And exit 2 discards any JSON you printed: choose exit codes or exit 0 with JSON, never both.

Matchers — the trap

How a matcher is evaluated depends entirely on which characters it contains.

ContainsEvaluated as
* or emptyMatch all
letters, digits, _ - , |Exact string, or a list separated by | or ,
anything elseJavaScript regex, unanchored
mcp__memory matches nothing. It contains only exact-match characters, so it is compared as a literal against mcp__memory__create_entities and fails.
Write mcp__memory__.* — the .* is what forces the regex path. Plugin-bundled servers are scoped differently again: mcp__plugin_<plugin>_<server>__<tool>.

Because regex matchers are unanchored, Edit.* also matches NotebookEdit. Use ^Edit$ for a whole-string match. Ten events ignore matchers entirely, including Stop, UserPromptSubmit, PostToolBatch and TeammateIdle.

A hook end to end

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [
          { "type": "command",
            "if": "Bash(rm *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh",
            "args": [] }
        ] }
    ]
  }
}
#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Destructive command blocked by hook"
    }
  }'
else
  exit 0   # no decision — the normal permission flow applies
fi

The if field uses permission-rule syntax and avoids spawning the process at all when it doesn’t match. It checks each subcommand, strips leading VAR=value assignments, and looks inside $() and backticks — but it fails open on anything it cannot parse. Use it for efficiency, never as a security boundary.

Rewriting, not just blocking

  • PreToolUse → updatedInput replaces tool arguments before execution.
  • PostToolUse → updatedToolOutput replaces the tool’s result.
  • MessageDisplay → displayContent changes what is shown, not what is stored.
  • PermissionDenied → retry: true tells the model it may try again.

The first two are the redaction layer: strip secrets outbound before they reach a third-party MCP server, scrub anything sensitive inbound.

Injecting context

additionalContext passes a string into the window wrapped in a system reminder, capped at 10,000 characters. Two rules:

  • Write facts, not commands. “The deployment target is production” reads as project information. Text framed as an out-of-band system instruction can trip Claude’s prompt-injection defences, at which point it is surfaced to you instead of used.
  • It is replayed, not re-run, on resume. Timestamps and commit SHAs go stale. SessionStart hooks do re-run on resume.
OrderingPermissionRequest fires after PreToolUse, and only on the “ask” path — if PreToolUse already allowed or denied, it never fires at all. It also does not fire in non-interactive mode, so automated permission decisions belong in PreToolUse.

Where hooks live

User settings, project settings, local settings, managed policy, plugin hooks/hooks.json, and skill or subagent frontmatter. They merge rather than replace — user and project hooks add to managed ones. Enterprise controls: allowManagedHooksOnly, allowedHttpHookUrls, and a disableAllHooks that cannot disable managed hooks from outside managed settings. /hooks shows everything active and where it came from.

Frontmatter hooks are the interesting scope: a subagent carries its own enforcement, so a low-autonomy agent physically cannot push, regardless of what it is asked to do.

08  MCP & skills

Tools from MCP, judgement from skills.

MCP gives Claude purpose-built tools for an external system with connection and auth handled by the server. A skill teaches it how to use them well — your schema, your query patterns, your formatting rules. They are complements, and pairing them is where most of the leverage sits.

Scopes and precedence

ScopeStoredShared
localYour machine, this projectNo
project.mcp.json in the repoYes — supports env-var expansion
userAll your projectsNo

Precedence is local > project > user. Managed configuration (managed-mcp.json, allowlists and denylists) sits above all three.

claude mcp                        # configure servers
claude mcp login sentry           # OAuth without opening /mcp
claude mcp login sentry --no-browser   # prints the URL — for SSH
/mcp reconnect <server>
/mcp disable <server>             # turn off without removing
claude --strict-mcp-config --mcp-config ./mcp.json

Things worth knowing

  • Tool search is on by default, so idle servers cost almost nothing. Schemas load on demand.
  • Claude Code can be an MCP server, exposed as a tool to other clients.
  • Servers can push — channels deliver notifications into a running session and can relay permission prompts elsewhere. Research preview.
  • Elicitation lets a server request user input mid-tool-call; hooks can intercept both the request and the response.
  • Long tool calls are backgrounded automatically. Output limits can be raised per tool.

Skill anatomy

---
name: deploy
description: Release checklist for the production stack
disable-model-invocation: true   # only you can trigger it — zero context cost
context: fork                    # run in isolated context
---

1. Confirm the changelog entry exists
2. …

Skills live in .claude/skills/ and ~/.claude/skills/, load live from disk, and can be chained — up to six at once, with the trailing text passed to each as arguments. Use disable-model-invocation for anything with side effects: it saves context and guarantees only you fire it.

Descriptions are the interfaceClaude chooses skills by matching your task against their descriptions. Vague or overlapping descriptions are the reason a skill “doesn’t trigger”. Write the description for the moment of selection, not as a title.

09  The Agent SDK

The same harness, as a library.

The Agent SDK runs Claude Code’s loop inside your own process, in Python or TypeScript. Both bundle a native Claude Code binary. From any other language, run the CLI as a subprocess with -p --output-format json.

If you’re…Use
Building an agent without writing the tool loopAgent SDK
Working interactively from a terminalClaude Code CLI
Calling the API and owning the loop yourselfClient SDK
Running long agents without operating sandboxesManaged Agents

Rule of thumb: if you are writing a tool-execution loop by hand and the tools are file, shell and search operations, the Agent SDK has already done that work.

Message types

TypeEmitted
SystemMessageLifecycle. Subtypes: init, compact_boundary, informational, worker_shutting_down
AssistantMessageAfter each response, including the final one
UserMessageAfter each tool execution, carrying results
StreamEventOnly with partial messages enabled
ResultMessageEnd of the loop: text, usage, cost, session ID

In TypeScript, AssistantMessage wraps the raw API message — content blocks are at message.message.content, not message.content. A few trailing system events can arrive after ResultMessage, so iterate to completion rather than breaking on the result.

A production-shaped agent

from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage

async for message in query(
    prompt="Find and fix the bug causing test failures in the auth module",
    options=ClaudeAgentOptions(
        allowed_tools=["Read", "Edit", "Bash", "Glob", "Grep"],
        setting_sources=["project"],   # loads CLAUDE.md, skills, hooks
        max_turns=30,
        max_budget_usd=5.00,
        effort="high",
    ),
):
    if isinstance(message, ResultMessage):
        if message.subtype == "success":
            print(message.result)

Result subtypes

SubtypeMeaningresult?
successFinished normallyYes
error_max_turnsHit the turn limitNo
error_max_budget_usdHit the spend limitNo
error_during_executionAPI failure or cancellationNo

Always check the subtype before reading result. Every subtype still carries total_cost_usd, usage, num_turns and session_id, so you can bill and resume after a failure. stop_reason reports why the model stopped: end_turn, max_tokens, or refusal.

settingSources is the bridgeOne option — setting_sources=["project"] — makes an SDK agent inherit CLAUDE.md, skills, filesystem hooks and subagent definitions from the repo. A workflow refined interactively in Claude Code becomes a productised agent without a rewrite.

Deployment notes

  • Stateless hosts — pass a sessionStore adapter so transcripts mirror to your own backend and any host can resume. Point CLAUDE_CONFIG_DIR at a temp directory if the local copy must be ephemeral.
  • Custom tools default to sequential. Set readOnlyHint in the annotations to unlock concurrency.
  • Budget by default. Subagent spend counts toward the cap; once reached, further subagents fail and running ones are stopped.
  • Terms — use is governed by Anthropic’s Commercial Terms. Third-party products may not offer claude.ai login or rate limits without prior approval; use API-key auth. “Claude Agent” and “Powered by Claude” are permitted branding; “Claude Code” is not.

10  Practice & pitfalls

The habits that compound, and the traps that don’t announce themselves.

Seven habits

  1. Give it something to verify against. Tests, types, a linter, a running app.
  2. Explore, plan, then code. Plan mode is read-only and therefore cheap.
  3. Delegate, don’t dictate. Outcome and constraints, not step-by-step instructions.
  4. Manage context aggressively. Subagents for high-volume reading; /clear between unrelated tasks.
  5. Promote repeated corrections into structure. Twice → CLAUDE.md. Third playbook paste → a skill. Second repo → a plugin.
  6. Enforce with hooks, guide with prompts. “Always” and “never” in a prompt are hooks you haven’t written.
  7. Add an adversary. A reviewer whose job is to find the flaw.

Pitfalls

  • Hook exit code 1 does not block. Only exit 2 does — except WorktreeCreate, where any non-zero aborts.
  • Exit 2 discards your JSON. Pick one signalling mechanism per hook.
  • mcp__server as a matcher matches nothing. You need mcp__server__.*.
  • Regex matchers are unanchored — Edit.* catches NotebookEdit.
  • The if filter fails open on unparseable Bash. It is not a security boundary.
  • additionalContext phrased as a system command can trip prompt-injection defences.
  • Switching model mid-session invalidates the prompt cache. So does changing effort.
  • A deny rule with a bare tool name removes the tool entirely; a scoped rule only denies matching calls.
  • ${CLAUDE_PLUGIN_ROOT} changes on every plugin update — persist state in ${CLAUDE_PLUGIN_DATA}.
  • Instructions from early in a long session may not survive compaction. Persistent rules belong in CLAUDE.md.

Self-test

  1. Why does a matcher of mcp__github never fire?
  2. Your hook detects a policy violation and exits 1. What happens?
  3. Which is cheaper over a long session: 400 lines in CLAUDE.md, or the same content as a skill? Why?
  4. Name three actions that invalidate the prompt cache and two that don’t.
  5. When would you reach for an agent team rather than parallel subagents?
  6. You need a rule that must hold on every single tool call. Where does it go, and why not CLAUDE.md?
  7. What does setting_sources=["project"] pull into an SDK agent?
  8. Which permission mode never prompts but still denies anything unapproved?
